# 第 1 题：Agent 后端的 Redis 设计（答题稿）

## 一、题目

> 传统后端架构里，后端是最后一层，Redis 的核心任务是给高频请求做加速。
> 但 agent 时代的后端不再是最后一层，大部分业务逻辑被 agent 处理了。
> 这种情况下，后端 + agent 框架的 Redis 要如何设计？

## 二、核心论点（先亮结论）

Redis 的角色从「缓存加速器」升级为「Agent 运行时的共享状态中枢 + 异步协调层」。

传统架构里 Redis 是锦上添花：挂了顶多变慢，miss 了回源重算即可。Agent 架构里 Redis 变成了运行时的承重墙：它承载对话状态、任务队列、检查点、幂等去重，一旦丢了，可能丢对话、丢任务、重复执行有副作用的工具。

因此本题的答案主线不是「罗列 Redis 能存什么」，而是讲清楚「为什么角色变了，以及每一种新角色用什么结构、怎么保证可靠」。

## 三、为什么角色变了

| 维度 | 传统后端 | Agent 时代 |
|---|---|---|
| 请求形态 | 无状态、短、同步 | 有状态、多轮、长耗时、异步 |
| 后端位置 | 最后一层，直接回给用户 | 中间协调层，LLM 与工具在「后面」 |
| 业务逻辑归属 | 全在后端代码 | 大部分被 LLM/Agent 决策替代 |
| Redis 主要用途 | 缓存热点数据、session、限流 | 状态中枢：session、检查点、队列、流式、幂等、记忆 |
| 一致性要求 | cache miss 回源即可 | 状态一致 + 可恢复，对话/任务不能丢 |
| 失败影响 | 变慢 | 丢状态、重复副作用、卡死流程 |

三个根本变化：

1. **请求变「有状态」**：一个用户输入不再是一个请求，而是一个跨多轮、可能持续数秒到数分钟的流程。状态必须能跨进程、跨重启存活。
2. **调用变「昂贵 + 异步」**：LLM 调用有 token 成本和高延迟，工具调用慢且可能有副作用，不能像传统缓存那样随意重算，必须缓存、排队、去重。
3. **后端变「协调者」**：后端从「最后执行者」变成「编排层」，需要在 LLM、工具、前端之间传递状态和事件，Redis 天然适合做这个共享的中枢。

## 四、总体架构与 Redis 的定位

```
用户/前端
   │  SSE / WebSocket（流式事件）
   ▼
后端接入层（网关）
   │
   ▼
Agent Runtime（主循环：组装 context → 调 LLM → 解析 → 调工具 → 回填）
   │            ▲                    │
   │            │                    │
   ▼            │                    ▼
 LLM 服务 ◄─────┘              工具服务（异步 worker）
                                  ▲
                                  │ 消费任务
                             ┌────┴─────────┐
                             │    Redis     │
                             │ 状态中枢+协调 │
                             └──────────────┘
                                   ▲
                                   │ 异步落库 / 对账
                                   ▼
                              数据库（事实源）
```

Redis 在这里是**热状态层**：读写快、可过期、可重建，但不承担「唯一事实源」的角色（事实源是 DB 或事件流）。这句话在一致性部分会展开。

## 五、Redis 承担的八大职责

### 5.1 Session 状态与对话历史

**要解决的问题**：多窗口 session 隔离、随时续聊、断线恢复。历史不能只放进程内存，否则扩容、重启、灰度都会丢对话。

**方案**：

- `HASH` 存 session 元信息 + 当前状态机 step。
- `LIST` 存消息序列（user / assistant / tool 消息按时间序）。
- `HASH` 存工具私有状态（如 todo 列表），随 session 一起隔离。

**key 示例**：

```
agent:app:sess:{sessionId}:meta      # HASH: step、创建时间、max_turns 等
agent:app:sess:{sessionId}:msgs      # LIST: 对话消息
agent:app:sess:{sessionId}:tool      # HASH: 工具私有状态
```

**TTL 策略**：滑动续期——每次活跃 `EXPIRE` 重置，长期不活跃再异步归档到 DB，Redis 只保留热会话。

### 5.2 异步工具任务队列

**要解决的问题**：工具耗时长（搜索、外部 API、子 LLM），同步等待会卡死主循环，违背第 3 题的「首 token 2 秒」要求。

**方案**：Agent 主循环把工具调用丢进队列，worker 异步执行，结果写回后再通知主循环继续。

- `STREAM` + Consumer Group：可 ack、可重放（PEL 挂起列表重投）、可靠，适合有状态任务。
- `LIST` + `BRPOP`：简单，但消费者崩溃会丢任务、无 ack，只适合容忍丢失的轻量场景。
- `PUB/SUB`：只做「结果好了」的通知，不承载任务本体。

**key 示例**：

```
agent:app:taskq:{priority}            # STREAM: 任务队列
agent:app:task:{taskId}:result        # STRING: 结果回填
```

### 5.3 检查点 / 断点恢复

**要解决的问题**：长任务中断后不能从头重放（LLM token 太贵，还可能重复触发工具副作用）。

**方案**：每个 step 完成后把运行时状态快照写入 Redis，带版本号；崩溃后从最近检查点恢复，而不是重头再来。这是 LangGraph 等框架 checkpoint 机制的简化版，Redis 是它的轻量存储载体。

**key 示例**：

```
agent:app:ckpt:{sessionId}            # STRING: 序列化快照 + version
```

**TTL**：中等（如 24h），覆盖「任务仍在进行」的窗口。

### 5.4 LLM / 工具结果缓存（精确 + 语义）

**要解决的问题**：LLM 调用昂贵，相似问题重复调用是纯浪费。

**方案分两层**：

1. **精确缓存**：`STRING`，key = 工具名 + 参数 hash + 模型版本，命中直接返回。
2. **语义缓存**：把 query 转 embedding，用向量索引做相似度检索，相似问题直接命中上次结果。Redis 的 RediSearch VSS / Vector Set 可承担向量存储。

**权衡**：LLM 输出非确定性，语义缓存必须带「相似度阈值 + 版本 + 短 TTL」，且对「会随真实世界变化的查询」（如实时价格）要关闭缓存，不能无脑命中。

**key 示例**：

```
agent:app:cache:tool:{tool}:{argHash} # STRING: 精确结果缓存（短 TTL）
agent:app:idx:embedding               # 向量索引: 语义缓存
```

### 5.5 幂等去重与并发控制

**要解决的问题**：重试不重复下单；同一 session 并发执行多个 step 会写乱对话历史。

**方案**：

- 幂等去重：每次工具调用生成 `toolCallId`，`SET NX PX` 抢占幂等 key，重复请求直接返回已缓存结果，覆盖重试窗口。
- 并发控制：同一 session 用分布式锁 `SET NX PX`（value 带 owner 标识，释放时校验避免误删），保证同一时刻只有一个 step 在执行。
- 原子性：所有「读-判-写」组合用 Lua 脚本保证原子，避免竞态。

**key 示例**：

```
agent:app:idem:{toolCallId}           # STRING: 幂等去重，TTL 覆盖重试窗口
agent:app:lock:sess:{sessionId}       # STRING: 分布式锁
```

### 5.6 限流 / 配额 / 熔断

**要解决的问题**：LLM 有成本与上游稳定性压力，需要按用户 / API key / 工具维度限流和配额。

**方案**：

- 滑动窗口：`ZSET`，score 为时间戳，`ZREMRANGEBYSCORE` 清窗口外 + `ZCARD` 计数（即第 6 题）。
- 令牌桶：`STRING` + Lua 原子扣减。
- 熔断：连续失败计数 `INCR` + 半开状态标记。

**key 示例**：

```
agent:app:rate:user:{userId}          # ZSET: 滑动窗口
agent:app:quota:key:{apiKey}:{model}  # STRING: token 配额
```

### 5.7 流式事件分发

**要解决的问题**：首 token、工具执行进度要实时推给前端（SSE/WS），不能让用户干等。

**方案**：

- `PUB/SUB`：轻量、低延迟，适合纯进度推送，但会丢消息、不持久。
- `STREAM`：持久、可回溯，适合「关键事件必须送达」的场景（如结果落库通知）。

**经验法则**：进度类走 Pub/Sub，结果类走 Stream。二者混用，别把所有事件都塞进 Pub/Sub 然后发现丢了。

### 5.8 长期 / 共享记忆

**要解决的问题**：跨 session 记住用户偏好、历史事实。

**方案**：embedding 存向量库，召回后拼入 context；或 Redis 只存记忆元数据/指针，正文在向量库或 DB。

**key 示例**：

```
agent:app:mem:user:{userId}           # 向量 / 元数据
```

### 五节汇总表

| 职责 | 数据结构 | 关键点 |
|---|---|---|
| Session 状态 | HASH + LIST + HASH | 滑动续期 TTL，热数据留 Redis，冷数据归档 DB |
| 异步任务队列 | STREAM + Consumer Group | 可靠投递、ack、PEL 重试 |
| 检查点 | STRING（快照 + version） | 崩溃后从最近检查点恢复，不重放 |
| 结果缓存 | STRING + 向量索引 | 精确 + 语义两层，带版本和短 TTL |
| 幂等/并发 | STRING（SET NX PX）+ Lua | 幂等 key + 分布式锁，原子「读-判-写」 |
| 限流/熔断 | ZSET / STRING + Lua | 滑动窗口、令牌桶、熔断计数 |
| 流式事件 | PUB/SUB + STREAM | 进度走 Pub/Sub，结果走 Stream |
| 长期记忆 | 向量 / 元数据 | 召回拼 context，正文可外置 |

## 六、Key 命名规范与 TTL 分级

**命名分层**：`agent:{应用}:{资源类型}:{id}:{字段}`。统一前缀的好处是运维排查、批量清理、监控 key 分布都方便。

**TTL 分级**（不要一刀切）：

| 数据 | TTL 策略 |
|---|---|
| 会话状态 | 滑动续期，活跃即续，长期不活跃归档 |
| 结果缓存 | 短（5~30 分钟），配合版本失效 |
| 幂等 key | 覆盖重试窗口（约 5 分钟） |
| 分布式锁 | 短（秒级），防死锁自动释放 |
| 检查点 | 中（约 24 小时） |
| 长期记忆 | 长期 / 不过期 |

## 七、一致性与降级设计（收尾重点）

**定位**：Redis 是「热状态层」，不是「唯一事实源」。事实源是 DB 或事件流。

**写策略**：

- 关键状态（对话历史、任务结果）写穿落库或异步落库，Redis 只是加速读。
- 缓存类数据写回即可，丢了重算。

**重建**：Redis 挂了或扩容重建时，从 DB / 事件流重放恢复热状态，而不是无中生有。

**降级**：核心对话不因 Redis 故障中断——

- 单机可降级到进程内存；多机可降级到 DB 直读。
- 缓存、队列、流式可降级为「跳过/同步直连」，牺牲性能保可用。
- 幂等与锁是「安全」组件，降级时宁可保守（加锁失败直接拒绝或串行），不能为了可用性放弃去重，否则重复下单。

## 八、一次对话请求的生命周期（Redis 介入点）

一次「查天气记待办」的请求里，Redis 在这些环节介入：

1. **收输入**：写 `session:msgs`，滑动续期 `session:meta`。
2. **抢锁**：`SET NX PX` 锁住 session，保证单 step 执行。
3. **组 context**：读 `session:msgs` 历史 + `session:tool` 工具状态 + 召回长期记忆。
4. **调 LLM**：流式 token 经 Pub/Sub 推前端；结果可命中语义缓存。
5. **解析出工具调用**：`SET NX` 幂等 key，去重后丢进 STREAM 队列。
6. **worker 执行**：结果写回 `task:result`，通知主循环。
7. **回填 + 写检查点**：更新历史，写 `ckpt` 快照。
8. **释放锁**，返回答案或继续 loop。

## 十、答题话术（两版）

**30 秒版（开场定调）**：

> 传统架构 Redis 是给无状态短请求做缓存加速；agent 架构下请求变成有状态的长流程，Redis 的角色升级为「共享状态中枢 + 异步协调层」。我把它承担的职责分成四类：状态（session、检查点）、异步（任务队列、流式事件）、成本（结果缓存、限流）、安全（幂等、并发锁）。每类我给出数据结构、key 设计和 TTL，最后落到「Redis 是热层不是事实源，如何降级」。

**5 分钟版（展开）**：按第五节顺序讲八大职责，每个给「结构 + key + TTL」一句话，最后用第七节收尾。
